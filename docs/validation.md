# Validation (`SkathIO.Rogue.Validation`)

`SkathIO.Rogue.Validation` checks a request before its handler runs, with code the SkathIO.Rogue
source generator writes into your project. There is no reflection, no assembly scan and no runtime
rule engine: each check is a plain method call, so it is AOT- and trim-safe, and a valid request
allocates nothing.

It sits next to [`SkathIO.Rogue.Validation.FluentValidation`](behaviors.md#validation-behavior),
which stays supported. You can use both in one project.

```bash
dotnet add package SkathIO.Rogue.Validation
```

The package carries only contracts. The code is generated by the core `SkathIO.Rogue` generator, so
keep both packages on the same major.minor version (`ROGUE013` warns when they differ). With project
references instead of packages, the project that declares `[Validate]` types needs the analyzer
reference described in [getting-started](getting-started.md#troubleshooting).

## Declaring rules

Mark the request `[Validate]` and `partial`, and put rule attributes on its properties:

```csharp
using SkathIO.Rogue;
using SkathIO.Rogue.Validation;

[Validate]
public sealed partial record CreateOrder : ICommand<OrderId>
{
    [NotEmpty, MaximumLength(50)] public string Reference { get; init; } = "";
    [GreaterThan(0)] public decimal Amount { get; init; }
    public Customer Customer { get; init; } = new();                       // [Validate] type: checked too
    [NotEmpty] public IReadOnlyList<OrderLine> Lines { get; init; } = [];  // each line is checked
    public int From { get; init; }
    public int To { get; init; }

    // Optional: cross-field and conditional rules in plain C#.
    private static void Rules(CreateOrder x, ref ValidationErrors errors)
    {
        if (x.From > x.To)
        {
            errors.Add(nameof(From), "order.window.reversed", "The window starts after it ends.");
        }
    }
}

[Validate]
public sealed partial record OrderLine
{
    [NotEmpty] public string Sku { get; init; } = "";
    [GreaterThan(0)] public int Quantity { get; init; }
}
```

`[Validate]` works on every request kind (`ICommand`, `ICommand<T>`, `IQuery<T>`) and on any class,
record or struct used inside one. It must be `partial`, as must any type that contains it, because the
validator is generated into the type itself. That is what lets it call your `private` `Rules` hook.

### Built-in rules

| Attribute | Applies to | Fails when |
|-----------|------------|------------|
| `[NotEmpty]` | `string`, collections, `Guid` | null, empty or whitespace-only string, empty collection, `Guid.Empty` |
| `[MinimumLength(n)]` | `string`, `IReadOnlyCollection<T>` | fewer than `n` characters or items (null passes) |
| `[MaximumLength(n)]` | `string`, `IReadOnlyCollection<T>` | more than `n` characters or items (null passes) |
| `[GreaterThan(x)]` | numbers and nullable numbers | not greater than `x` (null passes) |
| `[LessThan(x)]` | numbers and nullable numbers | not less than `x` (null passes) |

Every rule takes optional `Code` and `Message` named arguments that replace its default code and
message: `[NotEmpty(Code = "order.reference.missing", Message = "Give a reference.")]`.

A non-nullable reference property (in a `#nullable enable` context) that holds `null` fails with the
code `not_null`, and its other rules are skipped. A nullable one (`string?`) is left to its rules.

### Writing a rule

A rule is an attribute deriving from `RuleAttribute` whose logic lives in static members, so the
generated code calls them directly and no attribute instance is ever created:

```csharp
public sealed class StartsWithAttribute : RuleAttribute
{
    public StartsWithAttribute(string prefix) => Prefix = prefix;
    public string Prefix { get; }

    public const string DefaultCode = "starts_with";
    public static string DefaultMessage(string propertyName, string prefix) => $"'{propertyName}' must start with '{prefix}'.";
    public static bool IsValid(string? value, string prefix) => value is null || value.StartsWith(prefix, StringComparison.Ordinal);
}
```

`IsValid` takes the value and then the attribute's constructor arguments in order. Add one overload
per property type the rule supports; a generic overload such as `IsValid<T>(IEnumerable<T>? value)`
works too. `DefaultMessage` takes the property name and the same arguments, and is called only when
the check fails. Placing a rule on a property it has no `IsValid` overload for is a build error
(`ROGUE015`).

### Nested objects and collections

A property whose type is a `[Validate]` type is validated in turn, as is each item of an array or
`IEnumerable<T>` of `[Validate]` items. Error paths use the ASP.NET format: `Customer.Name`,
`Lines[2].Sku`. A `[Validate]` type from another project is validated the same way, provided that
project was also built with the generator (`ROGUE017` otherwise).

Lists declared as `IReadOnlyList<T>` or `IList<T>` are walked by index, and arrays, `List<T>` and
other concrete collections with `foreach`, so the walk allocates no enumerator. A property declared
as a plain `IEnumerable<T>` allocates the enumerator its collection returns.

## Async rules

Rules that need services or I/O go in a class implementing `IAsyncRules<T>`:

```csharp
public sealed class CreateOrderChecks(IOrderRepository orders) : IAsyncRules<CreateOrder>
{
    public async ValueTask CheckAsync(CreateOrder x, ValidationErrors errors, CancellationToken cancellationToken)
    {
        if (await orders.ReferenceExists(x.Reference, cancellationToken))
        {
            errors.Add(nameof(x.Reference), "order.reference.taken", "Reference already used.");
        }
    }
}
```

The generator registers each concrete `IAsyncRules<T>` class it finds in the project as **Scoped**
(the same lifetime the FluentValidation package uses for validators), with `TryAddEnumerable`, so a
hand registration of the same class is kept. Rules registered by hand from other assemblies run too:
the dispatcher resolves every `IAsyncRules<T>` in the request's scope.

## Order of the checks

1. Rule attributes on the request and, recursively, on its nested objects and collection items. Every
   failing property is reported, not just the first.
2. The `Rules` hook, only if step 1 found nothing, so it can rely on the attribute rules.
3. Each `IAsyncRules<T>`, only if steps 1 and 2 found nothing, so they can assume a well-formed
   request and no database call is made for one that is already invalid.

All of this runs inside the request's generated dispatch, before the handler is resolved and before
any pipeline behavior or processor. A request that fails throws `RogueValidationException`; the
handler does not run.

## Handling the failure

`RogueValidationException.Errors` lists every error (path, code, message). `ToProblemDictionary()`
groups the messages by path in the shape ASP.NET's validation problem takes:

```csharp
app.Use(async (context, next) =>
{
    try
    {
        await next(context);
    }
    catch (RogueValidationException ex)
    {
        await Results.ValidationProblem(ex.ToProblemDictionary()).ExecuteAsync(context);
    }
});
```

The exception message names only the failing paths, never messages or values, so logging it does not
copy request data into your logs.

## Performance

A valid request allocates nothing in validation: the error list is created on the first error, and a
path such as `Lines[2].Sku` is built only for a part that failed. A request without `[Validate]` is
generated exactly as before, so it keeps its zero-allocation dispatch path. Both are held by the
generator tests. See [benchmarks](benchmarks.md#validation-engines) for a comparison with
FluentValidation.

## Diagnostics

| ID | Severity | Meaning |
|----|----------|---------|
| `ROGUE014` | Error | A `[Validate]` type, or a type that contains it, is not `partial`. |
| `ROGUE015` | Error | A rule attribute cannot check the property it is on (no fitting `IsValid`, or the rule lacks `DefaultCode`/`DefaultMessage`). |
| `ROGUE016` | Error | A method named `Rules` is not `static void Rules(T x, ref ValidationErrors errors)`. |
| `ROGUE017` | Error | A `[Validate]` type comes from an assembly built without the SkathIO.Rogue generator, so it has no validator to call. |
| `ROGUE018` | Warning | Rule attributes or an `IAsyncRules<T>` are declared for a type without `[Validate]`, so they never run. |

## Limits

- Validation runs for commands and queries dispatched through Rogue (`ISender.Send`, `IMediator`,
  `SendObject`, and the generated `Send{Request}` methods). It does not run for events, stream
  queries or requests handled through the `SkathIO.Rogue.MediatR` compatibility interfaces, and not
  when you construct or bind a request elsewhere.
- Rule arguments must be attribute constants. Use the `Rules` hook for anything else.
- A cyclic object graph inside a request is walked without a guard. Requests built by a JSON
  deserializer are trees, so this does not arise in practice.
